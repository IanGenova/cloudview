# ULTRA — CloudView, 10 September 2026

A deep inspection of the system as built, not of a diff. Three stages gated each
other: does it start, what happens to the data, what is wrong with the code.

**Inspected:** git HEAD `6ed55fe` ("Accrue loyalty on the goods, and give the rule one
home"), clean `git clone`, 247 TypeScript files / 110,162 lines, 30 migrations, 3 test
files.

**Verdict: not ready to be trusted with a pilot.** It starts and it serves real
traffic, and several of its hardest parts — the inventory deduction, the loyalty
ledger, the webhook token check, the tenancy guards on dashboard actions — are
genuinely well built. But a fresh environment cannot be created from this repository
at all, a hotel administrator can make themselves a super administrator, the
guest-facing order page ships the hotel's payment merchant id and Wi-Fi password to
anyone who views source, and the running Next.js has two unauthenticated remote-code
-execution advisories against it.

| Severity | Count | Meaning |
|---|---|---|
| **BLOCKER** | 9 | ships something broken |
| **MAJOR** | 31 | wrong under real conditions |
| **MINOR** | 14 | works, will bite |

**Status counts:** 45 open · 7 fixed · 2 blocked · 0 stale · 0 wont-fix

Every finding carries a stable id (`BLOCKER 3`, `MAJOR 7`) assigned here, and a status
line — the only part of this document that is edited afterwards.

## BLOCKERS

### BLOCKER 1 — A hotel admin can make themselves super admin, and take over any other tenant's account
`src/lib/backups/restore.ts:174-186`, `:412-431`
**Status:** `fixed · phase 1 · 2026-09-10`

`prepareUserContext` loads **every user in the database with no hotel filter** and indexes them by email. `restoreUsersAndPermissions` then matches archive rows by email and writes `role: backupUser.role` straight from the uploaded file. The archive is not signed — `readAndVerifyBackupZip` only checks `checksums.json` against the files shipped beside it in the same zip, and the uploader controls both.

**Failure.** A HOTEL_ADMIN at hotel A (the default permission set grants `HOTEL_SETTINGS` full, which is what gates both upload and restore) builds a zip whose `manifest.hotelId` is hotel A — so the ownership check in `src/lib/backups/service.ts:222` passes — and whose `modules/users-permissions.json` holds one row: their own id and email, `"role": "SUPER_ADMIN"`, `"isActive": true`. They POST it to `/api/backups/upload`, then run restore with `confirmation=RESTORE`. Line 419 executes `db.user.update` and sets their role to SUPER_ADMIN. `authVersion` is not incremented, so no logout is forced; they sign out, sign in, and `loginDirectAction` mints a JWT with `role: SUPER_ADMIN` read from the database. They now hold every hotel in the estate. The same primitive retargets any other tenant's administrator by email — set `hotelId` to their own hotel to move the account, or `isActive: false` to disable it.

**Do:** scope the email lookup and the update to `targetHotelId`; never take `role` from the archive — clamp to the row's existing role, or to STAFF/KITCHEN; bump `authVersion` on any change. Sign the archive with an HMAC over the checksums.

### BLOCKER 2 — No environment can be built from this repository
`prisma/migrations/20260613013848_connect_rewards_to_nfc_guest_sessions/migration.sql:28`, `prisma/migrations/20260713_xendit_payment_cutover/migration.sql:8-9`
**Status:** `blocked · needs migrations written and verified from empty — ultra never writes a migration`

`prisma migrate deploy` against an empty database fails twice.

**First failure**, migration 23 of 30, MySQL error 1091, `Can't DROP 'Order_guestMemberId_fkey'`. The migration's `RedefineIndex` pair assumes the FK helper index and the new index coexist. On MySQL 8.4 they do not — creating an index whose definition is identical to an auto-created FK helper index *renames* the existing one rather than adding a second. Reduced to a minimal reproduction and executed:

```sql
CREATE TABLE GuestMember (id VARCHAR(191) NOT NULL, PRIMARY KEY(id));
CREATE TABLE `Order` (id VARCHAR(191) NOT NULL, PRIMARY KEY(id));
ALTER TABLE `Order` ADD COLUMN guestMemberId VARCHAR(191) NULL;
ALTER TABLE `Order` ADD CONSTRAINT `Order_guestMemberId_fkey`
  FOREIGN KEY (guestMemberId) REFERENCES GuestMember(id);
--  indexes here: Order_guestMemberId_fkey, PRIMARY
CREATE INDEX `Order_guestMemberId_idx` ON `Order`(guestMemberId);
--  indexes now:  Order_guestMemberId_idx, PRIMARY   <- the _fkey index is GONE
DROP INDEX `Order_guestMemberId_fkey` ON `Order`;
--  ERROR 1091 (42000): Can't DROP 'Order_guestMemberId_fkey'
```

**Second failure**, after stepping past the first, migration 25, MySQL error 1054, `Unknown column 'paymentMethod' in 'servicerequest'`. The cutover alters `ServiceRequest.paymentMethod`, a column **no migration in the repository creates**. It failed on statement 2 of roughly 20, so the whole Xendit payment schema behind it never ran.

**And the drift is far wider than those two.** Comparing the fully-applied chain against `schema.prisma` produced a 587-line repair script: **12 tables and 37 columns that the application depends on are created by no migration in the repository.**

```
SeriesCodeCounter         GuestStayFolioLine        PosPayMongoSession
ServiceRequestAttachment  GuestStayFolioPayment     PayMongoWebhookEvent
GuestStay                 GuestStayDevice           GuestPayMongoSession
GuestStayFolio            DashboardNotification     GuestPayMongoRefund
```

That is the entire guest-stay/folio subsystem and the entire payment-session subsystem. They exist on the running database only because they were applied by hand.

**What this costs:** disaster recovery from the repository is impossible; a staging or QA environment cannot be stood up; a second property or a white-label instance cannot be provisioned; and a new developer cannot get a working database.

**Do:** this needs migrations written, which is outside what this inspection may do. Reconcile the chain deliberately — generate a squashed baseline from `schema.prisma`, verify it applies to an empty database, and add a CI job that migrates from empty on every push so it cannot recur silently.

"xenditCommissionType":"PERCENTAGE_NET",

### BLOCKER 5 — Ingredient stock only ever goes down
`src/lib/inventory.ts:76-82`
**Status:** `fixed · phase 1 · 2026-09-10`

**Proven live.** Order `ULTRA-1`, 2 × Signature Burger, released to the kitchen: Burger Bun 100 → 98, Beef Patty 60 → 58, two `ORDER_DEDUCTION` movements. Cancelled through the dashboard's own Details → Cancel → Confirm Cancel: order `CANCELLED`, `inventoryDeductedAt` **still set**, Burger Bun **still 98**, Beef Patty **still 58**, and no reversing movement of any kind.

`src/lib/inventory.ts:81` is the **only** write to `InventoryItem.stockQuantity` in the entire application, and it is a `decrement`. There is no `increment` anywhere. The cancellation path calls `restoreMenuStockForCancelledOrder`, which restores `MenuAvailabilityStock` — a different subsystem. `inventoryDeductedAt` is never cleared. `InventoryMovementType.STOCK_IN`, `STOCK_OUT` and `ADJUSTMENT` are never written by any code path.

And there is no way to put stock back: none of the seven server actions in `src/app/dashboard/inventory/actions.ts` touches `inventoryItem` or `inventoryMovement` — they all operate on menu and service availability. The dashboard page titled "Inventory" is "Food Menu Stock Availability". `InventoryItem` is read only by the report export and the backup exporter. **The ingredient inventory the README advertises has no management screen at all.**

**Failure.** A hotel opens with 60 beef patties. Every cancelled-after-release order consumes ingredients that were never cooked. When the counter reaches zero, `deductInventoryForOrder` throws "Insufficient stock" on every burger order forever, and nobody in the building can fix it without a SQL client.

**Do:** two separate things. Restore ingredient stock on cancellation, with a reversing `InventoryMovement` and `inventoryDeductedAt` cleared, under the same conditional-claim pattern the deduction already uses. And build the stock-in screen, or delete the `InventoryItem` subsystem and the README's claims about it.

### BLOCKER 6 — A repeated payment webhook destroys a paid order and auto-refunds a good payment
`src/app/api/xendit/webhook/route.ts:283-317`, with `:225-234` and `:534-555`
**Status:** `fixed · phase 1 · 2026-09-10`

Line 283 reads the session status from a snapshot taken at line 248, then line 297 writes with `tx.guestXenditSession.update({ where: { id } })` — **unconditional on status**. Lines 228-233 deliberately let every repeat completion delivery fall through to that write, with the comment "Completed-payment delivery is intentionally replayable." The finalizer runs *after* the transaction commits, so the session sits in `PROCESSING` — visible to any concurrent delivery — for the whole duration of order creation.

**Failure.** T1 (`payment.succeeded`) reads the session as `PENDING`, writes `PAID`, commits, and enters `finalizeGuestFoodXenditSessionById`, which claims `PAID → PROCESSING` correctly and begins the order transaction. T2 (`payment.capture`, or Xendit's retry after the 503 at line 632) reads the session, now `PROCESSING`; line 283 sees `PROCESSING !== COMPLETED`, so line 297 **writes it back to `PAID`**, wiping the claim. T1 then reaches `guest-food-order.ts:547`, whose `updateMany({ where: { id, status: PROCESSING, orderId: null } })` matches zero rows, throws, and rolls back the entire order transaction — no order, no items, stock decrements undone. T1's catch calls `markGuestPaymentFinalizationFailedAndRefund`, which sets `PAID_REVIEW_REQUIRED` and **dispatches a full automatic refund to Xendit** for a payment where nothing was wrong.

The idempotency row is written after all side effects and outside the transaction, so it never gates this path.

**Do:** make line 297 a conditional claim in the house style — `updateMany({ where: { id, status: { in: [PENDING, PAID, PAID_REVIEW_REQUIRED] } } })` — and treat `count === 0` as "another delivery owns this session", never overwriting `PROCESSING` or `COMPLETED`.

### BLOCKER 7 — A partially-refunded order is billed again on the guest's folio at checkout
`src/app/dashboard/guest-stays/actions.ts:919-925` (duplicated at `src/app/dashboard/guest-stays/page.tsx:86`)
**Status:** `fixed · phase 1 · 2026-09-10`

`getOrderOutstandingCents` returns 0 only when `paymentStatus === PAID` (or the order is cancelled, or not yet READY/DELIVERED). `PARTIALLY_REFUNDED`, `REFUND_PENDING` and `REFUND_FAILED` all fall through and are billed as outstanding.

**Failure.** A guest on stay S orders two items at ₱5.00 through the NFC portal. At 10% service charge and 12% VAT the order is `subtotal 1000 / sc 100 / tax 120 / total 1220`, created `PAID` with `guestStayId: S`. The guest cancels one item on the tracking page while the order is still PENDING; the track page refunds ₱6.10 and rewrites the order to `total 610`. `recalculateGuestRefundStateTx` sets `paymentStatus = PARTIALLY_REFUNDED`. The kitchen delivers. At checkout the folio posts a `FOOD_ORDER` line of **305 centavos** for an order the guest already paid ₱12.20 for and was refunded ₱6.10 on — a **₱3.05 double charge** — and `checkoutGuestStayAction` then flips that order to `PAID`, erasing the evidence.

**Do:** return 0 for any `paymentStatus` other than `UNPAID`. Fix both copies.

### BLOCKER 8 — The same function discounts an already-discounted total, halving room-charge revenue
`src/app/dashboard/guest-stays/actions.ts:954` (duplicated at `src/app/dashboard/guest-stays/page.tsx:121`)
**Status:** `fixed · phase 1 · 2026-09-10`

```js
return Math.round(order.totalCents * (activeItemSubtotal / originalItemSubtotal));
```

`order.totalCents` is *already* the post-cancellation total — both cancel paths rewrite `subtotalCents`/`serviceChargeCents`/`taxCents`/`totalCents` (`src/app/dashboard/orders/actions.ts:984-994`, and the guest track page) — while `originalItemSubtotal` is computed from the raw `quantity × unitPriceCents` of every item including the cancelled one. The discount is applied twice.

**Failure.** A ROOM_CHARGE order with items A ₱5.00 and B ₱5.00, `total 1220`. Staff cancels A while PENDING, so the stored order becomes `subtotal 500 / sc 50 / tax 60 / total 610`. The order reaches DELIVERED. At checkout `originalItemSubtotal = 1000` and `activeItemSubtotal = 500`, so the folio bills `round(610 × 0.5) = 305`. The guest owes ₱6.10 and is billed **₱3.05**. The hotel loses ₱3.05 on every folio containing an order with a cancelled item, and the order is then marked PAID in full.

**Do:** post `order.totalCents` directly — it is already authoritative — and delete the proration. Fix both copies.

### BLOCKER 9 — A hotel cannot change, or switch off, its own loyalty programme
`prisma/schema.prisma:1770` (`GuestPointSettings`), `src/lib/rewards.ts:12-16`, `src/lib/guest-point-sync.ts:28-36`
**Status:** `blocked · needs a point-settings screen, from the product owner`

The only two writers of `GuestPointSettings` are `upsert({ where, update: {}, create: {…} })` — they create the row once with hard-coded defaults and can **never** modify it. No server action, page or form writes this model; `saveHotelSettingsAction` touches only `HotelSettings`, and `dashboard/rewards/actions.ts` exports only catalogue, redemption, manual-adjustment and member actions.

**Failure.** `spendCentsPerPoint` is permanently ₱100 = 1 point. `minimumSpendCents` permanently 0. `nfcTapPoints` / `nfcDailyMaxPoints` / `nfcOncePerTagPerDay` permanently 1 / 3 / true. `guestStayCheckInPoints` permanently 10. `enabled` and `redemptionEnabled` permanently `true`. A hotel that wants to run 1 point per ₱50, or raise its minimum spend, or **stop issuing points at all**, cannot — there is no screen, and the two code paths that touch the row refuse to update it. The rate that determines the hotel's loyalty liability can only be changed by a developer with a SQL client. `pointsExpirationDays` is read by no code whatsoever, so points never expire and the column is decoration.

This is the same class of defect as BLOCKER 5: a business rule the product implies is owned by the business, and is not.

**Do:** add a point-settings form and server action on `/dashboard/rewards`, and give the two upserts a real `update` path.

## MAJOR

Each entry: the defect, then the concrete failure.

### MAJOR 1 — The repo's own start script makes every route unreachable
`src/middleware.ts:213`, `package.json:9`
**Status:** `open`
`shouldForceHttps` reads `request.nextUrl.hostname`, which under `next start -H 0.0.0.0` is the *bind* address, not the Host header. `0.0.0.0` matches none of the `localhost` / `127.0.0.1` / `10.` / `192.168.` / `172.16-31` exemptions. **Proven live:** with `start:http`'s own `-H 0.0.0.0`, `/`, `/dashboard`, `/dashboard/login`, `/t/room-305-main-panel` and `/api/qr` all returned `308 → https://0.0.0.0:3007/…`, which resolves to nothing. Rebinding to `127.0.0.1` fixed every one. Behind a proxy that sets `X-Forwarded-Proto: https` it works, which is why production has not noticed; any deployment without that header is dark. This is the same defect class as BT-01 and the nginx regression in `STATE.md`, fixed in `nfc-redirect-origin.ts` but never applied to the middleware that fronts every route.
**Do:** resolve the host from `X-Forwarded-Host` / `Host` via the existing `nfc-redirect-origin` helper.

### MAJOR 2 — A failed tag scan sends the guest, and the tag's secret, to a different origin
`src/lib/nfc-launch-handler.ts:527`, `:548`, `src/lib/nfc-public-url.ts:5-6`
**Status:** `open`
The accepted path was fixed to stay on the request origin; the verify and denial paths still build on `publicUrl()` — the *configured* origin. Line 548 puts the scan secret in the query string. **Proven live:** my local server returned `307 → https://cloudhotelph.com/n/room-305-main-panel/verify?k=<secret>&error=no_active_stay`, and the browser followed it to the real production host. `STATE.md` records the decision to leave these alone because "they carry no cookie, so the mismatch is harmless" — but they carry the tag's bearer credential, which lands in a different origin's access logs and in every intermediary. Any staging, QA or LAN deployment sends real guests to the production site.
**Do:** build these redirects on the request origin too, and strip `k=` from anything crossing an origin.

### MAJOR 3 — The room passcode has no brute-force protection
`src/lib/guest-stay-device-auth.ts:251`, reached from `src/app/n/[tagCode]/verify/actions.ts:121-126`
**Status:** `open`
`authorizeGuestStayDeviceWithPasscode` verifies a 6-digit passcode and mints a device cookie with no attempt counter, no lockout and no delay. The sibling path for public-location tags *does* have one — `requireRoomVerificationAttemptAllowed`, 5 failures then 15 minutes (`src/lib/guest-order-identity.ts:38-118`). **Failure:** a previous guest of room 301 keeps the launch URL in browser history; scan secrets survive checkout (only an explicit rotate changes them). After a new guest checks in, they replay `verifyGuestStayPasscodeAction` across 000000–999999 — ~500k requests, hours at a modest rate — and receive an authorized device cookie plus a full guest session for the current occupant's stay, then order room service to that guest's folio.
**Do:** apply the existing per-stay/per-IP limiter before `verifyGuestStayPasscode`.

### MAJOR 5 — Menu image upload takes its extension from the client, and `/uploads/` has no CSP
`src/app/dashboard/menu/actions.ts:201-212`
**Status:** `open`
The only content check is `allowedTypes.includes(file.type)` — the client-declared multipart Content-Type. The extension comes from the client-declared filename with no allowlist. Both sibling uploaders do this correctly (`hotel-guide/actions.ts:310`, `settings/actions.ts:29` map MIME → extension from a fixed list). `/uploads/` is served with **no Content-Security-Policy**: the middleware matcher excludes it (`src/middleware.ts:400`) and nginx serves the prefix directly with only `nosniff`. **Failure:** a STAFF user with MENU create permission posts `imageFile` with `filename="x.html"; Content-Type: image/png` and a `<script>` body. The file lands as `<slug>-<ts>.html` and the returned `imageUrl` reveals the name. Loading it executes attacker script on the app's own origin with no CSP; a HOTEL_ADMIN who opens it has their session driven. `.svg` works through the Next route too.

### MINOR 3 — The Cancellation Report prices the same event two incompatible ways
`src/app/api/dashboard/reports/export/route.ts:781-798` · **Status:** `open`
Order rows use `order.totalCents`; item rows use `cancelledQty × unitPriceCents` — subtotal only. A ₱12.20 order refunded in full reports "₱0.00" plus two ₱5.00 item rows if cancelled item-by-item, or ₱12.20 with no item rows if cancelled whole. Same money, two totals ₱2.20 apart.
**Do:** compute the impact from the associated refund amounts.

### MINOR 4 — Re-deriving the tax rate from rounded cents compounds
`src/app/dashboard/orders/actions.ts:786-792`, duplicated in the guest track page · **Status:** `open`
Each cancellation derives the rate from the previous step's already-rounded cents and rounds again. **Verified numerically:** a hotel at 12% VAT with an order of 100 items at 1 centavo (`subtotal 100, tax 12`), cancelled one at a time, leaves the stored tax pinned at **12** all the way down to `subtotal 23` — a **52.2% effective VAT rate** — where the correct figure is 3. Each step's refund is short by the same drift.
**Do:** read the rate from `HotelSettings` (or from a rate captured on the order) rather than back-solving it.

### MINOR 5 — Reward validity windows are anchored to the server's midnight
`src/app/dashboard/rewards/actions.ts:38-52` · **Status:** `open`
`new Date(\`${value}T00:00:00\`)` has no offset. On a UTC host a reward valid "11 Sep only" is live from 08:00 on the 11th to 07:59 on the 12th, Manila: a guest is refused at 07:00 on the 11th and succeeds at 07:00 on the 12th on an expired promotion. The read-back uses `toISOString()`, so fixing the host zone would then walk the date backwards on every resave.
**Do:** anchor both the write and the read-back to `+08:00`.

### MINOR 6 — The analytics stock table's status sort has no tiebreak
`src/app/dashboard/analytics/page.tsx:290-294` · **Status:** `open`
Both sort keys are low-cardinality and, unlike every sibling branch, this one appends no `product: { name }` tiebreak. With 24 items all at `availableQty = 0` and a page size of 10, a row can appear on both page 1 and page 2 while another is never rendered at all — the operator's stock list silently omits an item.
**Do:** append `{ id: 'asc' }`.

### MINOR 7 — Seven stale source backups are committed, including two copies of the middleware
`src/middleware.ts.backup-20260715-140437`, `…-143921`, `src/app/dashboard/tags/*.backup`, `*.before-origin-fix`, `NfcTagsClient.tsx.backup-…`, `_nfc-route-backup/` · **Status:** `open`
Five are inert. `_nfc-route-backup/` is **not**: `tsconfig.json` includes `**/*.ts` and excludes only `node_modules`, so both files are in the TypeScript program `next build` checks, and both import `@/lib/nfc-launch-handler`. A signature change there can fail the production build from a file that serves nobody. Two divergent copies of the authentication middleware sitting in the tree is its own hazard for whoever maintains that boundary next.
**Do:** delete them; git history has them.

### MINOR 8 — Dead NFC URL builders that encode the format known not to fit the chip
`src/lib/nfc-security.ts:463`, `:490` · **Status:** `open`
Both have zero callers; the live builders are in `nfc-public-url.ts`. `secureNfcLaunchUrl` still emits `/n/<hotelSlug>/<CODE>?k=<secret>` — the form `nfc-public-url.ts:347-374` documents as 146 bytes against an NTAG213's 136-byte budget, which is why the live builder drops the slug. A future caller reaching for the obvious-looking function reintroduces a deliberately fixed bug.
**Do:** delete both.

### MINOR 9 — The manifest pins nothing
`package.json:11-30` · **Status:** `open`
`next`, `react`, `react-dom`, `zod`, `clsx`, `lucide-react`, `qrcode` and most devDependencies are all `"latest"`. Only `package-lock.json` holds the build stable; `npm update`, a lockfile-less install, or any `npm i` can move majors with no diff in `package.json`. This is how the tree arrived at a Next.js version with two critical advisories against it (BLOCKER 3) without anything appearing to change.
**Do:** pin exact versions and let the lockfile agree with the manifest.

### MINOR 10 — `/api/qr` is the only QR generator and nothing calls it
`src/app/api/qr/route.ts` · **Status:** `open`
No reference anywhere but a directory listing in the README. The tags page shows a `QrCode` *icon* and tells staff they can reprint the QR link, but no QR image is rendered anywhere — so the tags module cannot actually produce one. Meanwhile the route is an unauthenticated `GET` that renders any attacker-supplied `http(s)` URL into a PNG served from the hotel's own domain with `max-age=86400`.
**Do:** wire it into the tags page behind a permission check and an allowlist, or delete it.

### MINOR 11 — `loginDirectAction` is unreferenced but still a live RPC endpoint
`src/app/dashboard/login/actions.ts:256` · **Status:** `open`
Zero references; the form uses `loginAction`. Because the file is `'use server'`, Next assigns this export a stable server-action id that remains callable by anyone who extracts it from the bundle. It goes through the same throttle, so it is not a rate-limit bypass — but it is an unreferenced, unmonitored second door to session creation. The same file still reads a `demoAccount` field no component sets.
**Do:** delete both.

### MINOR 12 — POS order creation enforces role but not the POS_TERMINAL permission
`src/app/dashboard/pos/actions.ts:1007-1011`, `:173-176` · **Status:** `open`
`createPOSOrder` calls `requireUser()`, and the internal function checks role and hotel scope but never `requireDashboardPermission(POS_TERMINAL, 'canCreate')` — unlike every other module. **Failure:** an admin unchecks POS Terminal for a STAFF account; that user is redirected away from `/dashboard/pos` but can still invoke the action directly and create paid orders, deduct stock and post room charges at their own hotel. Not cross-tenant.
**Do:** add the permission check.

### MINOR 13 — The deploy scripts disagree about where media lives
`deploy/setup-runtime-media.sh:5`, `:37-38`, `deploy/fix-cloudview-uploads.sh:125-141` · **Status:** `open`
One uses `/var/www/cloudview-media`, the other rewrites `.env` to `/var/www/cloudview-uploads/menu`; `CLOUDVIEW_MEDIA_ROOT` and `MENU_UPLOAD_DIR` are documented in neither `.env.example` nor the README, and `UPLOADS_ROOT_DIR` is written by a script and read by no code. With `MENU_UPLOAD_DIR` unset the writer falls back to `<cwd>/storage/menu-images` while the reader falls back to `/var/www/cloudview-media/menu` — **uploads succeed and every dish photo then 404s.**
**Do:** settle on one path, document both variables, delete the third.

### MINOR 14 — Dead schema and unreachable enum values
`prisma/schema.prisma` · **Status:** `open`
`MenuDailyStock`, `MenuDailyStockMovement` and the 7-member `MenuStockMovementType` are touched only by backup export/restore — superseded by `MenuAvailabilityStock`, which is what ships. `SubscriptionPackage` and `HotelSubscription` are round-tripped by backups and read by no application code, so `maxHotels`/`maxRooms` are unenforceable — a hotel on a 50-room plan can create unlimited rooms, and an unpaid account can never be suspended. `ServiceRequestAttachmentType.STAFF_BEFORE`/`STAFF_AFTER` can never be written, yet `ServiceRequestsClient.tsx:240-244` renders distinct badges for them — UI that can never display, because staff have no way to attach a before/after photo. `GuestStayFolioStatus.OPEN`, `DataBackupStatus.QUEUED`, `PosSyncStatus.RETRY` and the two `getNfcSessionPolicy` flags `allowMultipleDevices` / `keepUnresolvedPaymentsAlive` are likewise unreachable — the last means "private room tags allow one device" is a stated rule nothing enforces.
**Do:** decide per item: build it, or drop it so the schema stops implying controls that do not exist. **Dropping needs migrations.**

Also unreachable, harmless, worth deleting: `src/lib/xendit-payout.ts` (a complete Payouts v3 client with no importer), `src/lib/realtime/realtime-token-response.ts` (a duplicate of the live token minter), and roughly twenty orphaned exports across `src/lib/**` — listed in full in the working notes.
