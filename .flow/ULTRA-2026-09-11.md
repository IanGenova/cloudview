## MAJOR

### MAJOR 1 — Every NFC redirect on localhost goes to the production domain, because Next synthesises the header the resolver trusts
`src/lib/nfc-redirect-origin.ts:72-86`, `node_modules/next/dist/server/base-server.js:609`
**Status:** `open`

**Proven live.** On a fresh clone, README-literal env, bound to `127.0.0.1`:

```
/n/pool-deck-main-panel?k=<valid>   → 307 https://cloudhotelph.com/t/pool-deck-main-panel?nfcSession=1
/n/pool-deck-main-panel?k=WRONG     → 307 https://cloudhotelph.com/nfc-access-denied?reason=bad-secret
/n/room-305-main-panel?k=<valid>    → 307 https://cloudhotelph.com/n/room-305-main-panel/verify?k=<SECRET>&error=no_active_stay
```

The accept path drops the cookie it just set on `127.0.0.1` — the original BT-01 loop. The
verify path carries the tag's scan secret to another origin — the previous MAJOR 2, which
this inspection had marked fixed. With `Host: 192.168.0.130:3007` all three stay local.
With `X-Forwarded-Host: hotel.test` plus `X-Forwarded-Proto: https`, all three go to
`hotel.test`. Only loopback fails.

**Cause.** `resolveGuestRedirectOrigin` has two branches: a forwarded host means a proxy is
in front and loopback is a misconfiguration to be refused; no forwarded host means the
request URL is the browser's own address and loopback is honoured. That is a sound rule,
and the previous MAJOR 2 fix correctly pointed every denial and verify redirect at it. But
`next start` does this to every incoming request before any handler sees it:

```js
req.headers['x-forwarded-host'] ??= req.headers['host'] ?? this.hostname;
```

So the forwarded branch runs on **every** request, the "no proxy" branch is unreachable,
and loopback is always refused. The fifteen tests in `nfc-redirect-origin.test.ts` all
pass, because they feed the function hand-built inputs; none models what Next delivers.
`STATE.md` records BT-01 as "verified: entry on localhost:3005 now reaches the portal" —
that was `next dev`, or an older Next. Under the deployed version it does not.

**What it costs.** Production is unaffected — nginx sends a real, non-loopback
`X-Forwarded-Host`. LAN mode is unaffected. Local development of anything NFC is
impossible without `NFC_PUBLIC_APP_URL`, which the README's setup steps do not mention
(MINOR 5). And any future deployment reached over loopback without a proxy — a container
health check, an SSH tunnel, an on-box smoke test — sends guests to `cloudhotelph.com`
with their scan secret in the URL.

**Do:** in the forwarded branch, treat a loopback host as usable when it matches the
request's own `Host` — that is Next's synthesised value, not a proxy's. Add the case to the
test file with the exact header set `next start` produces. This is a small change to the
resolver; the callers are already right.

### MAJOR 2 — A line cancelled before the kitchen starts still has its ingredients taken
`src/lib/inventory-requirements.ts:34`
**Status:** `open`

**Proven live.** Order `CVDHFO000004`: one Breakfast Pancakes, one Signature Burger. The
burger line was cancelled from the dashboard while the order was PENDING — never released,
never cooked. The order was then accepted:

```
Sandwich Bread   120 → 117   (three pancakes across two orders — correct)
Burger Bun       100 →  99   (a burger that was never made)
Beef Patty        60 →  59   (a burger that was never made)
```

`buildRecipeRequirements` multiplies each recipe by `item.quantity` and never reads
`cancelledQty` or `status`. The previous repair pulled this into its own module so that
the new restore path would compute the same number as the deduction — and the comment
there says, in so many words, that both must use "the line's full ordered quantity". The
symmetry is right. The basis is wrong: the deduction should never have taken stock for a
line that was already cancelled, and the restore should give back exactly that.

**What it costs.** "The guest changed their mind before the kitchen started" is an
ordinary front-desk event, and every instance of it leaks the cancelled line's ingredients
permanently. The restore on whole-order cancellation gives back the full quantity, so that
path is consistent with itself — but a DELIVERED order cannot be cancelled, so the leak on
a partially-cancelled, delivered order is never recovered. This is the previous BLOCKER 5
surviving in a narrower form, and the repair pass wrote the line.

**Do:** use `Math.max(item.quantity - item.cancelledQty, 0)` and skip lines whose status
is CANCELLED, on both the deduction and the restore. Add the case to
`inventory-requirements.test.ts`: a cancelled line contributes nothing.

## MINOR

### MINOR 1 — A locked-out guest is told to try again
`src/app/n/[tagCode]/verify/actions.ts:129-133` · **Status:** `open`
The throttle works (stage 2). But the action maps only `INVALID_PASSCODE` and
`DEVICE_LIMIT_REACHED`; the new `PASSCODE_LOCKED` falls through to the generic "Unable to
authorize this device. Please try again or contact staff." — which, during a lockout, is
the one thing the guest should not do. The minutes-remaining message the throttle
composes is never shown. **Do:** map `PASSCODE_LOCKED` to `error.message`.

### MINOR 2 — Cash taken at the counter, order cancelled, nothing says the cash is owed back
`src/app/t/[tagCode]/track/[orderCode]/page.tsx`, `src/app/dashboard/orders/actions.ts` · **Status:** `open`
Order `CVDHFO000002`: `PAY_AT_COUNTER`, staff marked it PAID (₱317.20 in the till), guest
cancelled from the tracking page. Result: `paymentStatus PAID`, `totalCents 0`. A Xendit
order in the same position gets a `GuestXenditRefund` row and an automatic refund; a
cash order gets no record at all that ₱317.20 must go back to the guest. The cancellation
report shows the impact, but nothing tracks whether it was returned. **Do:** on cancelling
a PAID cash/counter order, write a `refund due` marker — a status, or a ledger row — that
a person can clear.

### MINOR 3 — README step 4 still names four variables
`README.md:101-123` · **Status:** `open`
`APP_URL` and `NEXT_PUBLIC_LAN_IP` stay at their production values and `NFC_PUBLIC_APP_URL`
is commented out in `.env.example`, so a developer following the steps literally hits
MAJOR 1 on their first NFC tap and has no way to know why. **Do:** add
`NFC_PUBLIC_APP_URL=http://localhost:3000` to step 4, with one sentence on why.

### MINOR 4 — Seven high advisories remain
`package.json` · **Status:** `open`
Zero critical now. The seven highs are all denial-of-service class and none is directly
imported at runtime: `brace-expansion`, `browserslist`, `shell-quote` (via `concurrently`,
a devDependency that only the dead `npm start` harness uses), and `deepmerge-ts` via
`@prisma/config` — the Prisma CLI, not the client. `npm audit fix` clears three; the Prisma
ones wait on upstream. **Do:** run `npm audit fix`; drop `concurrently` and
`local-ssl-proxy` along with the `start:https` script they exist for.

### MINOR 5 — `ecosystem.production.cjs` cannot be started the way its name suggests
`ecosystem.production.cjs`, `README.md` · **Status:** `open`
Observed on the production deploy: `pm2 start ecosystem.production.cjs` on pm2 7 runs the
file as a script and creates a process named `ecosystem.production`. pm2 only reads
`*.config.{js,cjs,json}` as ecosystem files. The refund-retry worker had to be started by
path with `--name`, and the README's deployment step still gives the command that does not
work. **Do:** rename to `ecosystem.production.config.cjs`, update the README and
`deploy/deploy.sh`.
